Context

先把业务说清楚，再写代码

很多人做练手项目卡在「不知道做什么」，因为需求太虚。这里给一套足够具体、又不用真去工厂调研的设定， 照着它你能把增删改查、状态流转、审批、附件、统计、权限全都串起来。

业务背景

公司里有几千件计量器具（卡尺、千分尺、压力表、扭矩扳手……）， 每件都有检定周期，到期必须送检。检定员要建工单、传报告， 主管要审批，到期没检的要被提醒，管理层要看合格率和及时率。

核心诉求：一件器具、一次检定、一条可追溯的工单。 所有复杂业务都是围绕这句长出来的。

核心实体与关系

  • 器具编号唯一、有量程与精度等级、挂使用部门与责任人
  • 工单一个器具的一次检定，有状态、有审批、有附件
  • 流程工单的状态迁移记录，含审批意见
  • 附件检定报告 / 现场照片，挂在工单上
  • 消息超期提醒、审批通知，推给具体的人

Contract

接口契约：先定好，再各写各的

前后端并行开发的前提是「契约先冻结」。下面是这套系统要用的统一返回体与几个关键接口， 实现时可以照着抄，也可以自己改 —— 但改了要同步告诉「对方」。

统一返回体 · Result<T>
{
  "code": 200,          // 200 成功；4xx 业务失败；5xx 系统异常
  "message": "success",  // 给人看的中文提示
  "data": { },            // 业务数据，失败时为 null
  "traceId": "a1b2c3"     // 排障用，日志里能查到这一整条链路
}
分页返回体 · PageResult<T>
{
  "records": [],     // 当前页数据
  "total": 128,     // 总条数
  "current": 1,     // 当前页（从 1 开始）
  "size": 10        // 每页条数
}
方法路径说明关键校验迭代
GET/api/ping连通性与版本—00
GET/api/work-orders分页 + 多条件查询时间范围、size ≤ 10001
POST/api/work-orders新建工单器具编号存在、日期顺序02
PUT/api/work-orders/{id}编辑工单（乐观锁）版本号一致、状态可编辑02
POST/api/work-orders/{id}/transition状态流转迁移合法、有权限03
GET/api/work-orders/{id}/logs操作日志时间线只看有权限的工单03
POST/api/files上传附件（multipart）类型白名单、大小、魔数04
GET/api/my/tasks我的待办按当前用户过滤05
GET/api/stats/summary统计汇总时间跨度 ≤ 1 年07
GET/api/work-orders/export导出 Excel（流式）条件必填、结果集上限07
状态流转 · 请求体示例
POST /api/work-orders/10086/transition
{
  "action": "REJECT",        // SUBMIT / APPROVE / REJECT / WITHDRAW / FINISH / CANCEL
  "comment": "报告缺少检定员签章",
  "version": 3              // 乐观锁：版本对不上说明别人改过了，直接拒绝
}

为什么要 version？两个人同时点「通过」，没乐观锁就会写两次日志、走两次流程。 加上它，第二次提交会收到「数据已被修改，请刷新」，这才是正确的行为。

Schema

表设计：别人给的，你也可以自己改

这是最小的可用结构。重点看三处：状态与审计字段（谁在什么时候改的）、 索引怎么建（查询条件决定索引）、日志表为什么要独立（业务表只存当前状态，历史不可变）。 

CREATE TABLE t_work_order (
  id            BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
  order_no      VARCHAR(32)  NOT NULL                COMMENT '工单号 WO+日期+序列',
  tool_code     VARCHAR(64)  NOT NULL                COMMENT '器具编号',
  tool_name     VARCHAR(128)                          COMMENT '器具名称',
  dept_id       BIGINT                                 COMMENT '使用部门，数据权限用',
  status        TINYINT      NOT NULL DEFAULT 0      COMMENT '0草稿 1待审 2通过 3驳回 4完成 9取消',
  result        TINYINT                                 COMMENT '检定结果：1合格 2不合格',
  plan_date     DATE                                    COMMENT '计划检定日期',
  finish_date   DATE                                    COMMENT '实际完成日期',
  version       INT          NOT NULL DEFAULT 0      COMMENT '乐观锁',
  deleted       TINYINT      NOT NULL DEFAULT 0      COMMENT '逻辑删除，布尔字段不带 is 前缀',
  create_by     VARCHAR(64),
  create_time   DATETIME     NOT NULL,
  update_by     VARCHAR(64),
  update_time   DATETIME,
  PRIMARY KEY (id),
  UNIQUE KEY uk_order_no (order_no),
  -- 索引跟着「列表页的查询条件」走：状态 + 计划日期 + 部门
  KEY idx_status_plan (status, plan_date),
  KEY idx_tool_code (tool_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT '检定工单';

-- 操作日志：只追加，不更新不删除。业务表存「现在」，日志表存「怎么变成现在的」
CREATE TABLE t_work_order_log (
  id            BIGINT      NOT NULL AUTO_INCREMENT,
  order_id      BIGINT      NOT NULL                COMMENT '工单 id',
  action        VARCHAR(32)                          COMMENT '动作',
  from_status   TINYINT                              COMMENT '迁移前状态',
  to_status     TINYINT                              COMMENT '迁移后状态',
  comment       VARCHAR(500)                         COMMENT '审批/驳回意见',
  operator      VARCHAR(64),
  operate_time  DATETIME    NOT NULL,
  PRIMARY KEY (id),
  KEY idx_order_time (order_id, operate_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT '工单操作日志';

自己动手改一改：把 tool_code 换成你熟悉的业务字段（比如设备编号、客户编号）， 表名跟着改，其余结构可以直接复用 —— 复杂业务的骨架其实是通用的。

Delivery

怎么算「这一轮做完了」

这是整套训练里最值钱的一段。代码写完不等于交付完， 用下面这份清单卡自己，练的是工程习惯。

  • 1接口先定契约 —— 动手前把请求 / 响应 / 错误码贴进 README 或接口文档，前后端据此并行。
  • 2后端先给 Mock —— 返回假数据的接口先跑通，前端不必等真逻辑。
  • 3正常 / 边界 / 异常各测一遍 —— 空列表、超大分页、超长时间跨度、重复提交、非法状态迁移。
  • 4前端三态齐全 —— 加载中、空数据、请求失败，缺一个都不算完。
  • 5后端不留裸异常 —— 抛出的每个异常都有 code 与中文提示，日志里有 traceId。
  • 6一个迭代一个分支 —— feat/01-list-page，合并前保证 npm run build 与 mvn -q compile 都过。
  • 7写清楚「这轮踩了什么坑」 —— 记进 README，下一轮你会回来感谢自己。
推荐节奏（一轮 = 一个循环）
  • ①读需求，把不确定的点写成问题（不要猜）
  • ②画表 / 定接口契约，10 分钟就够，别过度设计
  • ③后端写接口 + 自测（curl / Postman）
  • ④前端接接口，补三态与交互细节
  • ⑤按验收标准逐条过一遍，截图存档
  • ⑥提交、写清 commit message、开下一轮

commit 建议：feat(order): 工单列表分页与多条件查询、 fix(auth): 修正 token 过期后未跳登录。 别写「修改」「提交」「111」—— 半年后你自己都认不出来。

Pitfalls

这些坑我替你踩过了

都是这套项目里真实遇到过的，遇到时别怀疑人生，照着改就行。

🔌代理超时 / 502 —— 开发代理的 target 写 127.0.0.1 而不是 localhost，Node 会优先解析成 IPv6 ::1，而后端只监听 IPv4。
🪤代理把前端路由吃掉 —— 代理 key 必须写正则 ^/api/，写成 /api 会把 /api-demo 这类前端路由也转发给后端。
🔤JDBC 字符集报 UnsupportedEncodingException —— characterEncoding 填 Java 字符集名 UTF-8，不是 MySQL 的 utf8mb4。
🧵配了连接池却没有池依赖 —— spring.redis.lettuce.pool.* 需要额外引入 commons-pool2，否则启动时 NoClassDefFoundError。
🕐时间差 8 小时 —— 后端统一 serverTimezone=Asia/Shanghai + spring.jackson.time-zone，前端统一格式化成 yyyy-MM-dd HH:mm，别让两边各转一次。
💥循环依赖 / N+1 查询 —— 列表页用 select * 加循环查关联，1 页 10 条能打 11 次库；改成一次 join 或批量 in 查询。
📄导出大文件 OOM —— 别把百万行一次性 List 装进内存再写，用流式导出（EasyExcel / SXSSF）分批 flush。
🔁重复提交 —— 前端按钮禁用只是体验，后端还要靠唯一索引 + 乐观锁 + 幂等键兜底。
🚪越权访问 —— 光在页面藏按钮不算权限，每个接口都要校验「这条数据是不是你的」。改 id 就能看别人数据是最常见的漏洞。
🧊缓存与数据库不一致 —— 先更新库再删缓存，别反过来；缓存加过期时间，别指望它永远对。
